Problem → Approach → Result

The brief

Problem

Stock and requests fall out of sync

Blood inventory has to stay accurate in real time across multiple blood groups, while donor history and recipient requests both pull against — and update — the same stock numbers.

Approach

Push correctness into the schema

The MySQL schema was normalized with integrity constraints across donors, stock levels, and transactions — so invalid states are rejected at the database, not just the UI.

Result

A consistent, validated workflow

Donor registration, live inventory tracking across 8+ blood groups, and recipient request handling, with JavaScript form validation catching bad input before it reaches the database.

How it was built

Build sequence

1

Normalized schema design

Modeled donors, blood group stock levels, and transaction records as separate, related tables with integrity constraints between them.

2

Donor registration flow

Built the registration form and donor-history tracking, validated client-side before hitting the database layer.

3

Real-time inventory tracking

Wired stock levels across 8+ blood groups so every donation or request updates the same source of truth.

4

Recipient request management

Added recipient-side requests against live stock, with JavaScript validation guarding required fields and formats.

Reflection

What I'd do differently

This project predates my Spring Boot work — rebuilding it on Spring Boot and JPA today would let the integrity constraints I hand-wrote in SQL be expressed and tested at the service layer too, closer to how the E-shop project is structured.
